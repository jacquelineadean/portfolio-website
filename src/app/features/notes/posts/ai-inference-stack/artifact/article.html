The AI Inference Stack

Seven layers between your API call and a GPU

What each layer owns, the patterns it reuses, the numbers that bound it and how it fails.

Every LLM request crosses seven layers of software before a GPU multiplies anything. Most of those layers are plumbing you already know how to build: gateways, schedulers, caches, load balancers, compilers. The payload is new, and so are the limits it hits.

Each layer in the rack gets the same tabs. Overview explains the job. One or more interactive tabs let you run the mechanism. Spec lists what the layer owns, the classic pattern it reuses, the metrics to watch, the knobs to turn and how it fails. Practice ends with a quiz and a design drill.

Concepts · read this first

Five ideas explain most of the stack

Tokens, the two phases of a request, the KV cache, the latency metrics and the roofline. Each layer's design follows from these.

A request runs in two phases. Prefill reads the whole prompt in one forward pass. Every prompt token is processed in parallel, and each one writes its attention keys and values to the KV cache. Decode then produces the answer one token per forward pass. Each new token reads every cached key and value, then adds its own.

The phases stress different hardware. Prefill does a lot of math per weight it reads, so compute limits it. Decode does one token of math per request for every weight it reads, so memory bandwidth limits it. Almost every design choice in the stack is about one of these two facts.

The KV cache holds, for every token so far, the attention keys and values of every layer. Its size per token is fixed by the model's shape: two (keys and values) × layers × KV heads × head dimension × bytes per value. It grows linearly with prompt length and with the number of requests in memory.

That makes it the resource most layers fight over. The engine pages it. The platform routes by it and moves it between machines. Model designers shrink it with grouped-query attention and latent attention.

Four numbers describe an inference service. Time to first token (TTFT) is queueing plus prefill. Time per output token (TPOT), also called inter-token latency, is the decode step time one user sees. Throughput is tokens per second across every request. Goodput counts only the requests that met their latency targets, which is the number DistServe optimizes.

End-to-end latency for one answer is TTFT plus (output tokens − 1) × TPOT. Long answers are dominated by TPOT; short answers by TTFT.

A GPU has two speeds: how fast it can do math and how fast it can read memory. An H100 does 989 TFLOPS of dense BF16 math and reads 3.35 TB/s. Divide one by the other and you get the ridge point: a kernel must do about 295 FLOPs per byte of work per byte it reads before the math, and not the memory, becomes the limit.

Decode reuses each weight once per request in the batch, so its intensity is roughly the batch size. Prefill reuses each weight once per prompt token, so its intensity is roughly the prompt length. That single fact explains batching, chunked prefill, disaggregation and FP8.

L1Your app · the SDK call

Your code decides what reaches the GPU

The cheapest token is one that never needs computing. Prompt length, answer length and prompt order are all set here, before any infrastructure sees the request.

Every request starts as one SDK call. Your code builds the prompt from parts: tool definitions, the system prompt, documents, the conversation so far and the newest user message. Then it asks for a model, a token limit and a stream.

Three choices here move cost and latency more than most infrastructure work. The order of the parts decides how much of the prompt a cache can reuse. The token limit caps the most expensive tokens. Streaming shapes what the user feels as latency.

Anthropic's cache follows the order tools, then system, then messages; a change at one level invalidates that level and everything after it. Prompts shorter than a model's minimum (512 tokens to 4,096 tokens, depending on the model) are not cached at all, and no error says so.

response = client.chat.completions.create(
    model="...",
    messages=[tools, system, docs, *history, user],  ①
    max_tokens=1024,                                  ②
    stream=True,                                      ③
)
  1. ① Order. Caches match from the first token. Parts that never change go first.
  2. ② Length. Output tokens cost more than input tokens, and an answer cut off at the limit still returns success.
  3. ③ Streaming. Tokens reach the user as decode makes them, so the wait feels like time to first token.
L1Your appSpec sheet
Owns

Prompt assembly, model choice, token limits, streaming, and the latency your user feels.

Talks to its neighbors

Sends one request (messages, model, max_tokens, stream). Receives a stream of tokens and a usage record.

A pattern you already know

Cache-key design. A prompt prefix is a cache key, so it needs deterministic serialization, the way an HTTP cache needs stable URLs.

Watch these metrics
  • Input and output tokens per request
  • Share of input read from cache (cache_read_input_tokens)
  • Share of answers ending with finish_reason = length
  • Time to first token as the client sees it
Turn these knobs
  • Order of prompt parts
  • max_tokens and stop sequences
  • Streaming on or off
  • Model per task
  • Batch API for work that can wait
How it fails
  • Timestamps, request IDs or unsorted JSON keys at the front of the prompt make every request miss the cache
  • Unbounded conversation history grows cost and eventually overflows the context window
  • Non-streaming calls hit client timeouts on long answers
Decision boundary

Put retrieved documents before the conversation when they stay fixed for a session. Put them after when they change every turn, so the history stays cacheable.

Quick check

L2AI gateway · LiteLLM, Portkey

The front door counts tokens

An AI gateway looks like the API gateways web teams have run for decades. The unit of cost changed from the request to the token, and that changes every policy.

The gateway sits between your code and every model provider. LiteLLM puts more than 100 providers behind one OpenAI-style interface. Portkey adds retries, fallbacks, load balancing and guardrails, and claims under 1 ms of added latency.

A token stopped here never reaches a GPU, which makes the gateway the second-cheapest place to save money after your own code. It is also the only place that sees every call's cost, so it doubles as the system of record for spend.

L2AI gatewaySpec sheet
Owns

Authentication with virtual keys, quotas in tokens and dollars, routing across models and providers, retries and fallbacks, guardrails and the cost log.

Talks to its neighbors

Accepts OpenAI-style requests from many apps. Sends provider-specific requests out. Emits one cost record per call.

A pattern you already know

API gateway plus token-bucket rate limiter plus circuit breaker. The twist: the cost of a request is unknown until the answer finishes, so admission reserves an estimate and reconciles the real usage afterward.

Watch these metrics
  • Tokens per minute per key and per team
  • Spend per team against budget
  • Error, retry and fallback rate per provider
  • Latency the gateway adds
Turn these knobs
  • Limits in tokens per minute and requests per minute
  • Monthly budgets per key
  • Routing rules by model, price and health
  • Retry caps, backoff and timeouts
  • Fallback chains
How it fails
  • A retry storm re-bills every input token
  • A fallback model answers differently, so quality drifts silently
  • Limits counted in requests let one tenant with long prompts burn the shared budget
  • A buffering proxy breaks streaming
Decision boundary

Run a central proxy when many teams share providers and you need one budget and one log. Use the library inside the app when there is one app and the extra hop costs more than the governance is worth. LiteLLM ships both forms.

L3Inference platform · NVIDIA Dynamo, llm-d

A scheduler for the fleet

An engine runs one copy of a model on one machine. A platform runs many copies and decides which one gets each request, which GPUs do prefill and which do decode.

Scope is the cleanest test. A decision that needs to know about more than one replica belongs to the platform. NVIDIA Dynamo sits above vLLM, SGLang and TensorRT-LLM with a planner that resizes GPU pools, a router that sends requests where their KV cache already lives, a memory manager that offloads KV cache to cheaper storage, and NIXL, a library that moves KV cache between GPUs. llm-d builds the same ideas on Kubernetes, with vLLM as the engine and LMCache for offload.

Prefill and decode show up at two layers, and both copies earn their place. Inside one engine, the scheduler mixes the phases in each step so neither starves. Across a fleet, the platform can give each phase its own GPUs, sized and parallelized for its own bottleneck.

L3Inference platformSpec sheet
Owns

Replica selection across the fleet, KV-aware routing, prefill and decode disaggregation, KV transfer between GPUs, KV offload tiers and autoscaling per pool.

Talks to its neighbors

Receives requests from the gateway. Dispatches them to engine workers and moves KV cache between them.

A pattern you already know

A layer-7 load balancer with session affinity, plus a cluster scheduler, plus a distributed cache tier. Prefix affinity works like consistent hashing on the prompt's first blocks.

Watch these metrics
  • Prefix hit rate per replica
  • Queue depth and utilization per pool
  • KV transfer time between pools
  • Time to first token and time per output token per pool
  • Goodput: requests that met their latency target
Turn these knobs
  • Routing score: cache overlap against current load
  • Ratio of prefill GPUs to decode GPUs
  • KV offload tiers: GPU, CPU memory, SSD
  • Scale-up and scale-down thresholds per pool
How it fails
  • One popular system prompt pins traffic to one replica and creates a hot spot
  • Slow interconnect makes KV transfer cost more than it saves
  • Scaling down evicts warm caches and hit rate falls
Decision boundary

Split prefill from decode when prompts are long and both latency targets are tight. Keep them on one pool when prompts are short or the fleet is small, because the KV transfer then costs more than the interference it removes.

L4Inference engine · vLLM, SGLang, TensorRT-LLM

Keep the batch full

A GPU makes tokens cheaply only when it makes many at once, because each decode step reads every weight from memory whether the batch holds one request or two hundred.

Two papers built the modern engine. Orca scheduled one iteration at a time instead of one request at a time: a finished request leaves the batch at the next step, and a waiting one takes its seat. PagedAttention fixed the memory side. Engines had reserved one contiguous slab of KV cache per request, sized for the longest possible answer, and most of it sat empty. vLLM keeps the cache in small fixed-size blocks instead, allocated as the answer grows.

vLLM's V1 core, released in January 2025, folded these ideas into one scheduler. It treats prompt tokens and output tokens alike, gives each step a token budget and keeps prefix caching on by default. SGLang pushed prefix reuse further with RadixAttention. TensorRT-LLM, NVIDIA's engine, now defaults to a PyTorch backend.

Read the engine as an operating system for one model: a scheduler that time-slices every step, a virtual memory system for the KV cache, and an LRU cache for prefixes.

L4Inference engineSpec sheet
Owns

The per-step schedule (continuous batching, chunked prefill), KV memory (paged blocks, prefix cache, eviction), preemption, sampling and speculative decoding for one model replica.

Talks to its neighbors

Takes prompts and sampling parameters. Streams tokens back. Runs one replica, which may span several GPUs through tensor parallelism.

A pattern you already know

An operating system: a scheduler that time-slices every step, virtual memory with page tables and copy-on-write, and an LRU cache for prefixes.

Watch these metrics
  • Running and waiting requests
  • KV cache usage
  • Preemptions and recomputed requests
  • Tokens in each step's batch
  • Prefix cache hit rate
Turn these knobs
  • Token budget per step (max batched tokens)
  • Maximum concurrent sequences
  • GPU memory fraction for KV cache
  • Chunked prefill size
  • Tensor parallel size and quantization
How it fails
  • KV cache fills up, the engine preempts requests and throughput collapses
  • A large step budget lets long prefills raise time per output token
  • A small budget leaves the GPU underused
Decision boundary

Raise the batch until time per output token hits its target or the KV cache fills, whichever comes first. Past that point, add replicas.

Quick check

L5Framework · PyTorch

Where CPU overhead hides

PyTorch defines the forward pass. Below a certain batch size, the time the CPU spends launching GPU work can rival the work itself.

The framework holds the model: its layers, its attention variant, its mixture-of-experts routing, its weights. The engine calls the forward pass once per step. In eager mode PyTorch launches each operation from Python, one GPU kernel at a time, and decode kernels are small enough that the launches show.

Two tools cut that overhead. torch.compile fuses many small operations into fewer, larger kernels. CUDA graphs record a whole step once and replay it with a single launch. vLLM's V1 core uses both, including piecewise CUDA graphs, and credits lower CPU overhead for its 1.7× throughput gain over V0. TensorRT-LLM now runs on a PyTorch backend by default.

Model architecture choices also live here, and they ripple down the stack. Grouped-query attention gives every Llama 3 size 8 KV heads, which shrinks the KV cache. DeepSeek's latent attention shrinks it further, and its mixture of experts activates 37 billion of 671 billion parameters per token.

L5FrameworkSpec sheet
Owns

The model definition (attention variant, mixture-of-experts routing), weight loading, compilation, CUDA graph capture and the collective communication calls between GPUs.

Talks to its neighbors

Takes token IDs, positions and KV block tables as tensors. Returns logits for the next token.

A pattern you already know

A JIT compiler and runtime. Graph capture removes interpreter overhead the way a JIT removes the cost of dispatching each bytecode.

Watch these metrics
  • CPU time per step
  • Kernel launches per step
  • GPU idle gaps in a profiler trace
  • Compile and warm-up time at startup
Turn these knobs
  • torch.compile on or off
  • Batch sizes captured as CUDA graphs
  • Data type: BF16, FP8
  • Attention backend
How it fails
  • A new input shape triggers recompilation and a latency spike
  • Each captured CUDA graph holds GPU memory
  • A shape outside the captured set falls back to slower eager mode
Decision boundary

Capture CUDA graphs for the batch sizes you actually serve and pad to the nearest one. Capturing every size costs memory and startup time.

Quick check

L6Kernels · FlashAttention, FlashMLA, DeepGEMM, Triton

Kernels turn model tricks into speed

A kernel is a hand-tuned GPU program for one hot operation. Attention and matrix multiply take most of a forward pass, so their kernels set how close a model gets to the hardware's peak.

FlashAttention computes attention in tiles that fit in the GPU's on-chip memory, so the full matrix of attention scores never travels to HBM and back. FlashAttention-3, written for Hopper GPUs, reaches 740 TFLOPS in FP16, 75% of the H100's peak, and runs 1.5× to 2× faster than FlashAttention-2. Its FP8 path has 2.6× lower numerical error than a baseline FP8 attention method.

Model-specific kernels matter as much. DeepSeek's FlashMLA decodes its latent attention on Hopper GPUs, and DeepGEMM runs its FP8 matrix multiplies. Many newer kernels are written in Triton, OpenAI's Python-like language for GPU programs. The technique underneath is old: tile the work so it fits in fast memory, and fuse steps so intermediates never leave it.

L6KernelsSpec sheet
Owns

The hot loops: attention (FlashAttention, paged attention, FlashMLA), matrix multiply (cuBLAS, CUTLASS, DeepGEMM), expert dispatch, quantized matmuls and fused small operations.

Talks to its neighbors

Reads tensors from HBM, computes, writes results back, and tries to move as few bytes as possible.

A pattern you already know

Cache blocking and loop fusion from classic high-performance computing: work on tiles that fit in fast memory, and never write an intermediate you can recompute.

Watch these metrics
  • Achieved TFLOPS against peak
  • Achieved memory bandwidth against peak
  • Kernel time share in a profile
Turn these knobs
  • Kernel choice per shape
  • Tile sizes
  • Precision: FP16, BF16, FP8
  • CUDA, CUTLASS or Triton
How it fails
  • A new model shape has no tuned kernel and falls back to a slow path
  • Low precision loses accuracy without careful scaling
  • A kernel tuned for one GPU generation runs poorly on the next
Decision boundary

Write a kernel in Triton to get a fused operation working quickly. Move to CUDA or CUTLASS when the profile says that kernel dominates the step and the last stretch of speed pays for itself.

Quick check

L7GPU · H100, HBM, NVLink

Decode is a memory-bandwidth problem

An H100 can do far more math than its memory can feed during decode. Every layer above exists to keep this chip busy.

An H100 can do 989 TFLOPS of dense BF16 math but reads only 3.35 TB/s from its memory. To keep its tensor cores busy, a kernel must do about 295 FLOPs per byte of work for every byte it reads. Decode at batch size one does about one: each weight is read to make one token.

Meta's Llama model with 8 billion parameters is 16 GB of BF16 weights. One decode step takes at least 4.8 ms however fast the math is, so a lone user gets at most 209 tokens/s. Between GPUs, NVLink carries 900 GB/s inside a node; across nodes the network becomes the limit. DeepSeek's hardware paper estimates its model's decode ceiling at 67 tokens/s over 400 Gbps InfiniBand and 1,200 tokens/s on a GB200 NVL72.

L7GPUSpec sheet
Owns

Compute (tensor cores), memory (HBM capacity and bandwidth), and the links between GPUs (NVLink inside a node, InfiniBand or RDMA across nodes).

Talks to its neighbors

Runs kernels. Its physical limits set the ceiling for every layer above.

A pattern you already know

A memory hierarchy and the roofline model, the same reasoning as CPU caches against DRAM bandwidth.

Watch these metrics
  • Memory bandwidth utilization
  • HBM in use
  • NVLink and network traffic
  • Power and clocks
Turn these knobs
  • GPU model and count
  • Parallelism: tensor, pipeline, expert
  • Precision the hardware supports
  • Node and network topology
How it fails
  • Out of memory when weights plus KV cache exceed HBM
  • Expert-parallel all-to-all traffic saturates the network
  • Uneven expert load leaves one GPU as the straggler
Decision boundary

Split a replica across more GPUs when the model does not fit or one user's latency matters most. Add replicas when total throughput matters most, because every extra GPU per replica adds communication.

Quick check

Caching · across L1, L3 and L4

A cached token costs a tenth

Prefix caching is the same primitive at three layers: a provider's prompt cache, an engine's block cache and a platform's KV pool.

Anthropic launched prompt caching in August 2024. A prompt prefix marked for caching is written once at a 25% surcharge, then read back at 10% of the base input price for the next 5 min, a window that resets with each hit. Open-source engines give the same primitive away: vLLM's V1 keeps prefix caching on by default.

Under the hood it is PagedAttention's shared block, made findable. vLLM hashes each full KV block together with the hash of the block before it, so one hash names a block's entire prefix. A new request walks its own block hashes and reuses every block already in memory. SGLang keeps the same thing as a radix tree. Mooncake and LMCache extend it across machines, into CPU memory and SSD.

Cache read price10%of the base input price
Cache write surcharge25%once per entry
Cost cut, long prompts90%up to, per Anthropic
DeepSeek's cache hits56.3%of input tokens in one day

The book example caches 100,000 tokens of prompt: time to first token fell from 11.5 s to 2.4 s, a change of −79%.

Every Anthropic response reports cache_read_input_tokens and cache_creation_input_tokens. If both are zero, the prompt was not cached, and nothing else will tell you. Put the hit rate on a dashboard and check it after every prompt-template deploy.

Measure the hit rate, not the hope

A cache that silently misses costs the same as no cache. Track the share of input tokens read from cache, per route, before and after every template change.

Case study · DeepSeek-V3

Cheap tokens from every layer

DeepSeek serves a model with 671 billion parameters and published how, with one day of real cost and traffic numbers. It is the best public worked example of the whole stack tuned together.

The model is a mixture of experts: each token activates 8 experts of 256 experts routed experts per layer, so only 37 billion parameters work on it, one in 18. Its multi-head latent attention compresses the KV cache to 70.272 KB per token. The serving system splits prefill from decode and spreads the experts across many GPUs, so each GPU holds few experts and every batch stays large.

Read it layer by layer: model shape (L5) shrinks the cache, kernels (L6) make the shape fast, the platform (L3) splits phases and balances experts, and a disk-backed KV cache serves repeated prefixes.

Outsiders could check the recipe. In May 2025 the LMSYS team rebuilt it on 96 GPUs H100s with SGLang, splitting prefill from decode and spreading experts wide. They reached 22,300 tokens/s output tokens per second per node with 2,000 tokens of input, and estimated $0.2 per million output tokens, about a fifth of DeepSeek's own API price.

Failures · what the dashboard misses

The worst failures return 200 OK

A cold cache, a full KV cache or a truncated answer still returns a success code. The dashboards web teams already run stay green through all of it.

These failures share a mechanism: something changes the shape of the work without changing whether it succeeds.

The cache goes cold. A template edit puts a timestamp or a user name ahead of the system prompt. Anthropic's API also skips caching, with no error, for prompts under a model's minimum length (512 tokens to 4,096 tokens, depending on the model).

Memory runs out. Longer conversations fill the KV cache. The engine queues new requests, or preempts running ones and recomputes them later. Throughput falls; nothing errors.

Answers get cut off. A low max_tokens truncates responses with a success status.

Quality drifts. A new quantization, a chat-template mismatch or a model update changes the answers. Only an evaluation set catches it.

Cost · what a token costs

Cut the bill before buying a GPU

Enter your own bill and token mix, pull the levers each layer owns, and see the arithmetic behind every step.

On your own GPUs the bill is GPU-hours, and the cost of a token is the hourly price divided by the tokens that hour produced:

cost per million tokens = GPU price per hour × GPUs ÷ (tokens per second × 3,600) × 1,000,000

Everything that raises tokens per second per GPU lowers the cost of a token: bigger batches until memory runs out, FP8, prefix reuse, disaggregation. DeepSeek's published day makes it concrete: $87.1K of GPU time at $2 per GPU-hour served 608 billion input tokens and 168 billion output tokens. The LMSYS reproduction estimated $0.2 per million output tokens on H100s.

Pull the levers from the top down

Each layer down costs more engineering per dollar saved. Start with the prompt and the gateway, then the engine's settings, then the fleet, and buy GPUs last.
